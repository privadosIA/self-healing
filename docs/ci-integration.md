# CI integration

`healerd` reads findings from two scanners. SonarQube it asks directly; Trivy has no server API, so your pipeline **uploads** its report. This guide shows how, with example hosts only: replace `healer.example.com`, `gitea.example.com` and `sonar.example.com` with your own.

## The one rule that matters: upload before the pipeline fails

`healerd` starts working when Gitea tells it a job failed. If the Trivy report has not arrived by then, there is nothing to fix and the job ends `skipped` with *no fixable finding*. So:

1. run Trivy and write its report **without failing the step** (`--exit-code 0`),
2. upload the report,
3. only then run the step that fails the pipeline.

## Trivy with Gitea Actions

```yaml
name: security

on:
  push:
  pull_request:

jobs:
  trivy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      # 1. Scan and write the report. Do not fail here.
      - name: Scan
        run: |
          trivy fs --scanners vuln --format json --output trivy.json --exit-code 0 .

      # 2. Publish it to healerd. Runs even if the scan above had problems.
      - name: Publish the report to healerd
        if: always()
        env:
          HEALER_REPORTS_TOKEN: ${{ secrets.HEALER_REPORTS_TOKEN }}
        run: |
          curl --fail --silent --show-error --max-time 60 -X PUT \
            -H "Authorization: Bearer ${HEALER_REPORTS_TOKEN}" \
            --data-binary @trivy.json \
            "https://healer.example.com/reports/${{ github.event.repository.id }}/${{ github.sha }}"

      # 3. Now fail the pipeline if there is something serious.
      - name: Gate
        run: |
          trivy fs --scanners vuln --severity HIGH,CRITICAL --exit-code 1 .
```

Notes:

- The report URL is `PUT /reports/{repo_id}/{sha}`. `repo_id` is Gitea's numeric repository id, not the name, and `sha` is the full commit id of the commit being tested. In Gitea Actions these are `github.event.repository.id` and `github.sha`; check that your Gitea version fills them in for the events you trigger on.
- Find a repository's id with `curl -s -H "Authorization: token ${GITEA_TOKEN}" https://gitea.example.com/api/v1/repos/acme/widget` and read `"id"`.
- Store the token as a repository or organisation secret named `HEALER_REPORTS_TOKEN`, and set the same value as `HEALER_REPORTS_TOKEN` on the daemon. It is a separate credential from the webhook secret. **Without it on the daemon, the endpoint does not exist.**
- A new upload for the same repository and commit replaces the previous one. The daemon keeps the most recent 500 reports and deletes older ones.
- Reports larger than 20 MiB are refused.

Responses to the upload:

| Status | Meaning |
|---|---|
| `204` | Stored. |
| `401` | The bearer token is missing or wrong. |
| `400` | The repository id is not a positive number, the commit is not a hexadecimal id of 7 to 64 characters, or the body is not a Trivy JSON report. |
| `413` | The report is larger than 20 MiB. |
| `500` | The daemon could not store it. |

Test it from a shell:

```sh
curl --fail -X PUT \
  -H "Authorization: Bearer ${HEALER_REPORTS_TOKEN}" \
  --data-binary @trivy.json \
  "https://healer.example.com/reports/42/0123456789abcdef0123456789abcdef01234567"
```

### What a Trivy finding becomes

Only the `Vulnerabilities` of the report are used; misconfigurations and secrets are ignored. A vulnerability points at a dependency file, for example `go.mod`, not at a line. `healerd` places it at the first line of that file that mentions the package, and sends the model only the lines around it. If the package is not mentioned in the file (for instance an indirect dependency that appears only in a lock file), the job ends `skipped`.

Lock files are generated and should be regenerated by their package manager rather than edited. `HEALER_EXCLUDE_GLOBS` excludes `**/*.lock` by default; add `**/package-lock.json`, `**/pnpm-lock.yaml` or `**/go.sum` if you want those left alone too:

```sh
HEALER_EXCLUDE_GLOBS=**/*.lock,**/migrations/**,**/*secret*,**/package-lock.json,**/go.sum
```

## SonarQube

Nothing needs uploading: `healerd` asks SonarQube for the open issues. Set:

```sh
HEALER_SONAR_URL=https://sonar.example.com
HEALER_SONAR_TOKEN=changeme
```

and make sure of three things:

- **The project key is the repository name** without its owner: `acme/widget` is looked up as the SonarQube project `widget`. Set `sonar.projectKey` accordingly in your `sonar-project.properties`.
- **The analysis finishes before the webhook is useful.** `healerd` reports the issues of the latest analysis, so run the SonarQube scan before the step that fails the pipeline, as with Trivy.
- **Community Edition analyses the default branch only.** `healerd` therefore sends no branch parameter for the default branch and sends one for any other branch, which Community Edition cannot answer. Failures on other branches need a SonarQube edition with branch analysis.

The token needs permission to browse the project. Issues without a line number (file or project level) are skipped, because there is no snippet to show the model.

## Which finding is fixed

A job fixes **one** finding. Findings from all scanners are ranked by severity, then by how few lines they span, and the best one wins. Files matching `HEALER_EXCLUDE_GLOBS` are never chosen. The pull request says which finding it addresses, shows the old and new text, links to the code, and carries an unchecked *Reviewed by a human* item.

## Don't let the fix loop

A pull request from `healerd` runs your pipeline like any other. If that pipeline fails, the webhook for the `auto-fix/...` branch is ignored: `healerd` never tries to fix its own fixes. A person decides what happens next.
